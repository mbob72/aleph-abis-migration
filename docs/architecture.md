# Архитектура приложения

React → изолированный preload → Electron main → PTY → системный OpenSSH → сервер.
Обратный путь терминала: PTY → событие IPC → xterm.js. Проверка БД: React → IPC → pg →
бинарный SSH-канал → PostgreSQL. Команды НЗ используют сохранённые пути; обработка связей из интерфейса пока не запускается. Приложение не обращается к бэку `rsl-abis-service-v2`.

<a id="desktop"></a>

## Окно и мост Electron

<details>
<summary>React работает без Node.js<br>Preload предоставляет методы SSH, выбора ключа и проверки БД<br>Main проверяет отправителя IPC и владеет процессом</summary>

[createWindow](../electron/main.cjs#L17) создаёт единственное окно 1510×980,
минимум 1120×760, загружает локальную production-сборку Vite. Sandbox,
contextIsolation включены, nodeIntegration выключен. Новые окна и навигация
заблокированы. Закрытие окна, перезагрузка или падение renderer завершают локальную сессию.

[assertSender](../electron/main.cjs#L49) проверяет WebContents и главный frame
каждого IPC. Чужой отправитель получает исключение до выполнения операции.

[Мост preload](../electron/preload.cjs#L3) возвращает Promise для выбора ключа,
подключения, отключения и проверки PostgreSQL. Методы write/resize передают только данные терминала.
Подписки onData/onExit возвращают функции отписки. Renderer не получает общий
ipcRenderer, require, файловую систему или выполнение произвольного локального shell.

Обработчик `key:choose` открывает системный диалог приватного ключа в `~/.ssh` с видимыми скрытыми файлами и фильтром всех файлов, возвращает путь или null
при отмене. Содержимое ключей не читается приложением. validatePrivateKeyPath проверяет выбранный путь
сразу после диалога и повторно перед подключением; `.pub` отклоняется с пояснением.

</details>

<a id="ssh"></a>

## SSH и жизненный цикл процесса

<details>
<summary>Один локальный SSH-процесс на окно<br>Аргументы передаются массивом без shell<br>Вывод не используется для автоматического определения успешного входа</summary>

[buildSshArgs](../electron/ssh.cjs#L4) принимает объект SshProfile и возвращает
массив аргументов. Проверяет сервер, пользователя, целый порт 1–65535, абсолютный
путь приватного ключа без NUL/CR/LF; `.pub` отклоняется. При дефекте выбрасывает Error, процесс не запускается.
Разрешены DNS, IPv4 и IPv6; экзотические alias с пробелами не поддерживаются.

Используются `-tt`, `StrictHostKeyChecking=ask`, ConnectTimeout=15,
ServerAliveInterval=15, ServerAliveCountMax=3. При выборе приватного ключа добавляются
IdentitiesOnly=yes и `-i <путь>`; файл читает OpenSSH и сам запрашивает парольную фразу.
Предварительная загрузка ключа в SSH-agent не нужна.
Без выбранного ключа действуют стандартные identities.

validatePrivateKeyPath принимает абсолютный путь, отвергает `.pub` независимо от регистра
и управляющие символы. Существование файла, формат, права и парольную фразу проверяет
системный SSH; приложение не читает и не меняет ключи. Пользователь и порт
из формы передаются явно, имеют приоритет над SSH config.

[Обработчик ssh:connect](../electron/main.cjs#L90) сначала проверяет отправителя,
отсутствие активной сессии и параметры, затем запускает `/usr/bin/ssh` через node-pty.
Переменные окружения наследуются, чтобы SSH мог использовать SSH_AUTH_SOCK.
Начальный размер PTY 80×24, затем уточняется терминалом. Возврат `started`
подтверждает создание процесса, а не аутентификацию.

onData пересылает чанки в окно; границы чанка не совпадают с логическими строками.
onExit освобождает сессию и возвращает код завершения. События старого процесса
после его остановки игнорируются, чтобы не повредить новую сессию.

[stopSession](../electron/main.cjs#L58) сначала снимает ссылку, затем завершает PTY.
Вызывается отключением, закрытием окна и выходом из приложения; повторный вызов
без сессии ничего не делает. Серверные длительные задачи пока не запускаются.

Обработчик write принимает строку не более 65536 символов, resize — целые размеры
2–500 столбцов и 1–300 строк. Неверные данные игнорируются; без сессии оба метода
ничего не делают. Проверка БД использует бинарный SSH-канал, а команды worker — отдельные exec-каналы
с argv и структурированным результатом. Интерактивная PTY для них не используется.

</details>

<a id="terminal"></a>

## Терминал

<details>
<summary>xterm.js отображает реальный PTY<br>ResizeObserver согласует размеры окна и удалённого терминала<br>История ограничена 5000 строками в памяти</summary>

[TerminalPane](../src/TerminalPane.tsx#L8) получает running и callback onExit.
Первый effect создаёт xterm.js, FitAddon и подписки моста. Ввод пользователя
через onData передаётся в write, события SSH отображаются через term.write.
Код выхода дописывается в терминал и передаётся App. Ref exitHandler обеспечивает
актуальный callback без пересоздания терминала при каждом рендере.

ResizeObserver вызывает fit и resize при изменении контейнера. Cleanup снимает
подписки, отключает observer, освобождает terminal и обработчик ввода; это также
нужно для React StrictMode. Второй effect при открытии сессии ставит фокус,
показывает разделитель и уточняет размер PTY. Очистка экрана не закрывает SSH.

Без preload (браузер Vite) показывается сообщение о доступности SSH только в Electron.
Подтверждение fingerprint и ввод пароля выполняются оператором в терминале.
Приложение не сохраняет терминальный вывод в профиль или файл.

</details>

<a id="profile"></a>

## Профиль и форма

<details>
<summary>Сервер, БД и пути хранятся локально<br>Пароль БД сохраняется отдельно для выбранного подключения<br>Полнота формы не означает успешную проверку подключения</summary>

[loadProfile](../src/profile.ts#L16) читает `svetoch.migration.profile.v1` из localStorage,
накладывает только известные строковые поля на значения по умолчанию. Ошибка JSON,
хранилища или отсутствие профиля возвращают пустой профиль. Циклы проходят группы
и их поля; неизвестные ключи (включая password) не переносятся в результат. Старое поле publicKey также не переносится: после обновления
нужно выбрать приватный ключ, остальные известные поля профиля сохраняются.

[App](../src/App.tsx#L74) владеет черновиком Profile, отдельным состоянием пароля,
выбранным разделом и состоянием SSH. update меняет поле и снимает флаг сохранения.
Автосохранение и save вызывают persistProfile с белым списком полей и эффективными путями; пароль не является его полем. Ошибка localStorage
показывается уведомлением. Выбор ключа вызывает preload и меняет путь только
после подтверждения диалога; отмена сохраняет прежнее значение.

connect очищает сообщения, блокирует повторную кнопку на время Promise и открывает
SSH. Ошибка IPC/валидации/запуска показывается как alert; finally снимает busy.
disconnect закрывает SSH и обновляет состояние формы. Callback onExit сбрасывает
running и показывает код выхода. Подключение и вывод SSH остаются доступны независимо от заполнения параметров БД и файлов.
Проверка БД требует заполненной формы и запущенного SSH; фактическая готовность master проверяется в main.

[Field](../src/App.tsx#L34) группирует подпись, контрол и подсказку;
[SectionTitle](../src/App.tsx#L51) показывает номер, название и пояснение карточки.
Однотипные callbacks onChange передают строку в update, переключатели разделов
меняют представление, закрытие уведомления очищает сообщения. Проверка БД открывает read-only соединение. Отдельные команды НЗ могут запускать worker; stage/analyze меняют aut_import, но не вставляют прикладные НЗ в public. Состояния «пути заданы» и «параметры заданы»
проверяют заполненность, а не доступность БД и файлов.

</details>

## Ошибки и проверка

| Ситуация                      | След                                       | Поведение                                       |
| ----------------------------- | ------------------------------------------ | ----------------------------------------------- |
| Некорректный SSH-профиль      | Alert с текстом Error                      | Процесс не запущен, можно исправить и повторить |
| SSH завершился                | Код в терминале и уведомлении              | Кнопка подключения доступна снова               |
| Отмена выбора ключа           | Без сообщения                              | Прежний путь сохранён                           |
| Не удалось сохранить профиль  | Alert                                      | Черновик остаётся в памяти                      |
| Повреждённый сохранённый JSON | Пустой профиль                             | Можно заново заполнить настройки                |
| Просмотр в браузере           | Пояснение в терминале и alert при действии | SSH не запускается                              |

Серверных логов, JSON-отчётов, checkpoint и счётчиков записей в этой версии нет.
`npm test` проверяет границы аргументов SSH и отклонение внедрения опций.
`npm run test:desktop` проверяет настоящее окно Electron, изоляцию Node,
выбор приватного ключа без расширения через UI/IPC (ответ нативного диалога подменён),
отказ для .pub, отмену выбора, совместимость старого профиля, сохранение профиля отдельно от пароля, восстановление пароля и ошибку SSH на локальном порту 1. Рабочие серверы не используются.

## Выбор технологий

Electron позволяет локально запускать системный SSH без HTTP-сервиса на localhost;
React отвечает за интерфейс, node-pty — за интерактивную сессию, xterm.js — за её
отображение. Vite собирает локальные статические файлы. Стоимость выбора — размер
Electron и нативная зависимость node-pty. Проверенная целевая платформа первой
версии — macOS; установщики и поддержка других ОС пока не подготовлены.

<a id="pty-install"></a>

## Установка PTY

[scripts/prepare-pty.cjs](../scripts/prepare-pty.cjs#L5) запускается npm postinstall.
У поставляемого node-pty 1.1.0 helper в prebuilds может не иметь executable bit,
что приводит к `posix_spawnp failed` вместо SSH. preparePty на Unix проходит
только build/Release, build/Debug и prebuilds текущей платформы/архитектуры
в каталоге зависимости, добавляет существующему spawn-helper права выполнения.
На Windows ничего не делает. Ошибка изменения прав прерывает установку,
а не скрывается. Это изменение применяется и при чистом npm ci.

## Проверка PostgreSQL через действующий SSH

<details>
<summary>Только чтение: один SELECT, общий таймаут 10 секунд<br>Отдельный SSH -W канал без remote shell и локального порта<br>Пароль передаётся pg и не попадает в argv; форма сохраняет его локально</summary>

[Обработчик database:test](../electron/main.cjs#L179) проверяет отправителя, отсутствие
другой проверки, активный SSH, совпадение снимка SSH-профиля и существование
Unix master-сокета. Возвращает `{ok:false,message,durationMs:0}` при неготовности;
не пытается автоматически входить на сервер. Для принятой проверки создаёт
AbortController, вызывает testDatabaseConnection и освобождает блокировку в finally.

При ssh:connect создаётся собственный временный каталог с правами 0700 и сокетом,
передаются ControlMaster=yes и ControlPersist=no. Он доступен только в течение
этой PTY-сессии. [releaseSshContext](../electron/main.cjs#L66) отменяет проверку,
сбрасывает контекст и удаляет только этот каталог; вызывается stopSession,
завершением SSH и ошибкой запуска. При перезагрузке/закрытии renderer действует
та же очистка. Терминальный вывод не разбирается для определения готовности.

[validateDatabase](../electron/database.cjs#L12) проверяет типы и заполненность
хоста/имени/пользователя, целый порт 1–65535, четыре SSL-режима и строку пароля.
Запрещены NUL/CR/LF в реквизитах, NUL в пароле, пробелы и shell-метасимволы хоста.
Имя и пользователь передаются в pg как поля, не интерполируются в SQL.
Пустой пароль допустим. validateDatabase вызывается до создания процесса.

[buildDatabaseSshArgs](../electron/database.cjs#L45) получает уже проверенные параметры
БД, валидирует профиль SSH через buildSshArgs, добавляет сокет и `-W host:port`.
IPv6 заключается в скобки. BatchMode исключает запрос пароля, ProxyCommand=false
запрещает fallback к независимому входу при потере master. Пароль БД и SQL
отсутствуют в аргументах. TCP forwarding должен быть разрешён на SSH-сервере;
`127.0.0.1` относится к нему, а не к Electron или контейнеру worker.

[testDatabaseConnection](../electron/database.cjs#L143) принимает снимок SSH/БД,
пароль, ControlPath и AbortSignal. Для тестов допускается внедрение spawnProcess
и короткого timeoutMs; через IPC эти зависимости не принимаются. Создаёт pg.Client
с именем приложения svetoch-connection-test, read-only и statement_timeout=5000
в startup options. Пароль задаётся функцией, чтобы даже пустое значение не заменялось
локальными PGPASSWORD или pgpass. Общий таймер 10 секунд охватывает обе попытки SSL.

Выполняется фиксированный [SQL](../electron/database.cjs#L6): база, пользователь,
версия, серверный адрес/порт и SSL из pg_stat_ssl для текущего backend. Ошибки
аутентификации и запроса прекращают проверку. Нет импорта, DDL или проверки прав
на будущую запись в таблицы АБИС. Успех: `{ok:true,message,details,durationMs}`.
Ошибка: `{ok:false,message,durationMs}` с ограничением сообщения 1000 символов
и заменой буквального пароля на `[скрыто]`. Ошибки и конфигурация не логируются.

Режимы: disable — без TLS внутри SSH; prefer — TLS, повтор без TLS только при
точном ответе «The server does not support SSL connections»; require — TLS без
проверки сертификата; verify-full — доверенный сертификат и имя/IP сервера БД.
TLS поднимается локальным pg, поэтому CA — локальные доверенные CA Node.js,
а имя для проверки берётся из формы БД. Клиентские сертификаты и выбор CA пока
не реализованы. При verify-full, ошибке пароля/сертификата или сетевом сбое
понижения до plaintext нет.

Функции interrupt/abort уничтожают активный поток; после сбоя/успеха finally
уничтожает канал, закрывает pg.Client, снимает listener и таймер. Цикл SSL
перебирает не более двух режимов и останавливается после успеха или любого
отказа, кроме явного отсутствия поддержки SSL для prefer. Таймаут/AbortSignal
исключают следующую попытку. Терминальная PTY не закрывается проверкой БД.

</details>

<a id="database-stream"></a>

## Бинарный канал SSH для pg

<details>
<summary>Duplex вместо TCP-сокета для PostgreSQL-драйвера<br>Backpressure сохраняется между pg и SSH<br>Ошибки запуска, EOF и уничтожение освобождают дочерний процесс</summary>

[SshDatabaseStream](../electron/database.cjs#L81) получает массив аргументов и
spawnProcess (по умолчанию child_process.spawn). connect запускает /usr/bin/ssh
без shell, выдаёт connect после spawn и подключает stdout/stdin/stderr.
Синхронная ошибка запуска откладывается через queueMicrotask до установки
обработчиков pg. stdout выдаётся чанками через push; при заполнении буфера
чтение stdout приостанавливается, _read возобновляет его. Границы чанка не равны
границам сообщений PostgreSQL; framing и TLS обслуживают pg/Node.js.

_write передаёт чанк в stdin и ждёт callback записи, _final завершает stdin,
_destroy завершает дочерний SSH. setNoDelay/setKeepAlive возвращают поток:
физическим соединением и его keepalive владеет SSH master. stderr ограничен
4096 символами и используется при диагностике транспортного сбоя; в терминал
бинарный поток и реквизиты БД не отправляются. on close с ненулевым кодом
уничтожает канал с диагностикой. Ошибки каждого pipe также уничтожают его.
TLS error сохраняется отдельно: закрытие нижнего потока может опередить
ошибку проверки сертификата.

</details>

## Кнопка и актуальность результата

<details>
<summary>Проверить подключение → ожидание → успех/ошибка в карточке БД<br>Изменение реквизитов снимает прежний результат<br>Отключение SSH отменяет проверку и блокирует кнопку</summary>

[checkDatabase](../src/App.tsx#L104) делает снимок формы, отмечает ожидание,
вызывает preload.testDatabase и показывает результат только при совпадении
номера databaseEpoch. Во время ожидания поля БД и кнопка заблокированы.
[invalidateDatabase](../src/App.tsx#L99) увеличивает номер и очищает результат;
его вызывают изменения БД/пароля/SSH, подключение, отключение и завершение SSH.
Редактирование источников не сбрасывает проверку БД. finally снимает ожидание,
в том числе при отмене и ошибке IPC. Пароль и результат не входят в Profile
; пароль БД теперь отдельно сохраняется в localStorage по ключу подключения (см. ниже). При повторном запуске нужен новый вход SSH.

</details>

## Проверки БД

`npm test`: настоящий pg и PostgreSQL wire protocol на localhost, бинарный
Duplex с дочерним TCP-мостом вместо OpenSSH, read-only SQL, отсутствие пароля
в argv, пустой пароль без PGPASSWORD, отказ аутентификации, таймаут, отмена,
TLS require и отказ verify-full на одноразовом самоподписанном сертификате.
`npm run test:desktop`: настоящий Electron + локальный sshd с временными
ключами/known_hosts + ControlMaster + pg + протокольный стенд PostgreSQL.
Проверяются статус успеха/ошибки, сброс результата и удаление сокета.
Это не проверка рабочей БД: настоящего сервера PostgreSQL и рабочих данных
в стенде нет. Серверная конфигурация и пользовательские SSH-файлы не меняются.

Протоколы: [OpenSSH ControlMaster](https://man.openbsd.org/ssh_config#ControlMaster),
[pg custom stream](https://github.com/brianc/node-postgres/blob/master/packages/pg/lib/connection.js),
[параметры PostgreSQL](https://www.postgresql.org/docs/current/libpq-connect.html).

<a id="profile-storage"></a>

## Автосохранение и пути по умолчанию

[loadProfile](../src/profile.ts#L16) восстанавливает только известные строковые поля
ssh/database/source/processing, ошибки JSON/доступа возвращают исходный профиль.
[effectiveSources](../src/profile.ts#L7) заменяет пустые и пробельные пути значениями
[shared/defaults.json](../shared/defaults.json#L1). Этот же файл читает backend;
плейсхолдеры и фактические аргументы не расходятся.
[persistProfile](../src/profile.ts#L33) копирует только известные поля, записывает
эффективные пути в localStorage. Пароль и stdout отсутствуют в Profile. useEffect
App выполняет сохранение после изменения профиля; ошибка видна пользователю,
при отказе хранилища черновик остаётся в памяти. В processing сохраняются имя
worker/watcher, путь готового RSL10-пакета, UUID импорта и путь его stage-отчёта.
При загрузке автоматически не выполняются ни SSH, ни команды сервера.

<a id="authority-ui"></a>

## Папка НЗ и команды

[AuthorityPane](../src/AuthorityPane.tsx#L39) получает профиль, факт запуска SSH,
выбранный шаг и callbacks изменения настроек. Первый шаг проверяет Docker/worker,
второй содержит staging/analyze и подготовку DAT. Вложенный run отправляет только
разрешённый action; ожидание блокирует повторное нажатие. Ответ после изменения
контекста или размонтирования игнорируется через epoch/fingerprint. Проверки
готовности привязаны к SSH и контейнеру; изменение полей импорта не стирает
подтверждённый результат отчёта. Потеря ответа start требует явного status.
Обновление статуса выполняется кнопкой, без автоматического опроса сервера.

Справа вкладка «SSH» остаётся интерактивной, «Команды» получает потоковые события
IPC operations:event. Подписка снимается при размонтировании. В памяти удерживается
не более 200000 символов журнала; закрытие приложения не отменяет worker task.
[Сценарий оператора](authorities-workflow.md) описывает точный порядок кнопок.

<a id="remote-executor"></a>

## Исполнение отдельной SSH-команды

[runRemoteCommand](../electron/remote.cjs#L13) получает ssh, controlPath, массив argv,
AbortSignal и callback вывода; через IPC произвольный argv не принимается. Аргументы
экранируются POSIX quote, локальный child_process.spawn вызывается с shell=false.
Используются существующий ControlMaster, BatchMode и ProxyCommand=false: новый
вход при потере сокета не выполняется. Возвращается ok/exitCode/command/stdout/stderr.
stdout и stderr собираются чанками до 512 КиБ суммарно; каждый чанк также отправляется
в callback. EOF не означает успешную задачу: учитывается exit code команды.
Сбой spawn, timeout 15 секунд, AbortSignal и превышение лимита закрывают локальный
SSH-процесс, снимают listener/таймер и возвращают ошибку. Серверная задача могла
продолжиться; start не повторяется автоматически. Каждый цикл pipes обслуживает
два потока, не предполагая совпадения чанка с строкой. В команду пароль БД не входит.

<a id="authority-commands"></a>

## Allowlist worker и проверки запуска

[runAuthorityAction](../electron/authorities.cjs#L239) нормализует профиль, допускает
только container-status/worker-status/delivery-status/help, prepare-rsl10/rsl11,
inspect-package/check-worker-db/stage-rsl10/analyze-rsl10 и чтение task-log/task-report.
`settings` проверяет имена контейнеров и абсолютные пути. `containerPath` выбирает
самый длинный подходящий Docker mount и требует источник внутри /source.
`parseJson` отвергает не-JSON; `workerState` требует busy/accepting boolean;
`reportPath` допускает только нормализованный путь внутри /work/reports.

Перед prepare выполняются свежие inspect, worker status и test -f. Занятый,
остановленный или draining worker блокирует запуск. RSL10 использует numeric001,
RSL11 — rsl11-nafpn. task.id/stage/input ответа проверяются; старый task.id не
принимается как новый запуск. Worker выбирает /work/output/task.id независимо
от поля каталога экспорта; обратный mount даёт путь фактического результата на сервере.
Подготовка пакета не равна записи в БД.

main проверяет отправителя, активную сессию, совпадение SSH-профиля и master-сокет,
разрешает только одну команду НЗ одновременно. releaseSshContext отменяет локальное
ожидание, но не вызывает worker stop. При неопределённом start backend хранит
блокировку до явного worker status; после перезапуска нужно сначала прочитать
состояние, а не повторять start. Результат и ошибки показываются в карточке.

<a id="authority-staging"></a>

## RSL10: готовый пакет, stage и analyze

[AuthorityImportPane](../src/AuthorityImportPane.tsx#L12) показывает отдельную приоритетную карточку.
Путь пакета по умолчанию /work/output/authorities-2026-10-22/RSL10, это не исходный DAT.
`packagePath` разрешает /work и /source или переводит серверный путь по mount.
`validateRsl10Manifest` требует version=1, kind=abis-authorities, library=RSL10,
complete=true, limited=false, ready=true. Проверка манифеста не заменяет SHA-валидацию,
которую делает серверный stage.

`workerDatabasePaths` читает --db-env/--profile из Docker Config.Cmd (без Config.Env),
с defaults /run/db.env и /run/import-profile.json. check-worker-db вызывает
import check-db с этими путями. При stage повторяются проверки свободного worker,
пакета и ready БД; затем worker start --stage stage --input package. Применяется
подключение серверного worker, а не реквизиты отдельного UI test connection.
Пароль из формы не копируется и db.env не изменяется. Stage пишет aut_import;
успешный предыдущий stage того же пакета блокирует случайный повтор.

После completed/exit 0 task-report читает и подтверждает JSON-отчёт, в том числе
валидный импортный UUID, kind=authorities, status=prepared и manifest RSL10.
Возвращаются importIdRsl10 и stageReportRsl10, UI сохраняет их в настройках.
`validateRsl10Stage` повторно проверяет этот отчёт перед analyze, UUID не подменяется
worker task.id; затем запускается worker start --stage analyze --import-id UUID.
Именно worker назначает пути отчётов каждой новой задачи. Результаты выводятся
как JSON и task status. Автоматической цепочки нет; оставшиеся этапы запускаются отдельными кнопками (см. ниже).

Изолированные тесты: Node проверяет маршрутизацию, mounts, busy/drain, manifest,
UUID, потерю ответа и лимиты exec; Electron E2E использует localhost sshd и fake
Docker/worker. Рабочие серверы и реальные импорты в ходе разработки не используются.

<a id="task-observation"></a>

## Наблюдение за задачей и временная шкала

[TaskMonitor](../src/TaskMonitor.tsx#L54) получает ограниченную историю `TaskRecord`, ID последней проверенной задачи, доступность и callback `run`. Обрабатывает локальный выбор исторической задачи и показывает времена начала/окончания, часы компьютера, длительность, оценочный прогресс, сводку отчёта и раскрываемый лог. Эффект с интервалом 1 сек обновляет **только часы интерфейса**; при размонтировании очищает таймер. Ни mount, ни таймер не вызывают SSH. Кнопки читают текущую задачу worker; выбор строки истории не меняет цель команд, что явно подписано в интерфейсе. Ось графика общая для последних шести задач; бары соответствуют фактическим временам из worker. При отсутствии времён старого worker интерфейс показывает отсутствие данных вместо выдуманного интервала.

Модель [taskObservation.ts](../src/taskObservation.ts) обслуживает следующие контракты:

- `summarizeReport` принимает неизвестный JSON и оставляет только ID, kind, status, ready/dryRun/verified, безопасные числовые счётчики и текст ошибки. Исходные MARC-поля, профиль подключения и прочие поля не сохраняются.
- `mergeObservation` получает предыдущую историю, действие, IPC-результат и локальное время. Неуспешные результаты игнорируются. Снимки статуса, лога и отчёта объединяются только по `task.id`; несовпадение ID envelope и worker отвергается. Сохраняет последние 40 задач; при появлении новой задачи прошлый running помечается «Итог не получен», без выдуманного исхода или finishedAt, и его длительность больше не растёт; лог текущего сеанса ограничен 200000 символами. Отсутствующие данные следующего снимка не удаляют уже прочитанный отчёт/лог.
- `stamp`, `successful`, `running`, `duration` обслуживают разбор времени и отображение статуса. Успех требует completed/succeeded **и exitCode=0**; отрицательная длительность при расхождении часов ограничена нулём. Время начала/конца приходит с сервера, «сейчас» — часы компьютера оператора.
- `taskTiming` считает прошедшее время и медиану длительностей не более пяти успешных задач того же этапа и библиотеки, если она известна из input. Ошибки, нулевая длительность и другой этап не входят в выборку. При отсутствии истории оценка неизвестна, индикатор неопределённый. Для работающей задачи оценочный процент ограничен 95%; превышение прогноза предлагает обновить статус и не объявляет завершение. После завершения длительность фиксируется по finishedAt.
- `nextOperation` выдаёт серую подсказку следующего действия: сначала получить отчёт, затем следующий этап. Ошибка/ready=false/неподтверждённая проверка не продвигают маршрут. Подсказка не запускает команды. Кнопки запуска этапов расположены в AuthorityImportPane и не связаны с подсказкой автоматическим действием.
- `appliedReceipt` находит подтверждённый apply **того же import ID**: успешная задача, kind=authorities, status=applied, verified=true, dryRun=false и числовой insertAuthorities. Только этот отчёт подтверждает количество загруженных НЗ. План анализа и dry-run не являются записью. Поздравление появляется после успешного verify с verified=true и соответствующего подтверждённого apply; при уменьшении движения в настройках ОС конфетти отключено.
- `saveHistory` и `loadHistory` сохраняют/восстанавливают whitelist метаданных и счётчиков в localStorage. Ключ включает SSH host/port/user и контейнер; смена сервера не смешивает историю. Логи не сохраняются. Повреждённый JSON или недоступное хранилище дают пустую историю/работу в памяти, без исключения в UI. После перезапуска снимки помечены сохранёнными до ручного чтения worker status.

`AuthorityPane.run` объединяет наблюдения и отдельно сохраняет настройки импорта; успешные ответы трёх кнопок не дублируют JSON в общей карточке результата, ошибки остаются видимыми. Полный поток команд остаётся в правом терминале.

`runAuthorityAction` читает свежий worker status перед логом/отчётом, ограничивает пути `/work/reports`, затем повторно проверяет ID, этап и пути задачи. Смена задачи возвращает ошибку без observation, поэтому файл не прикрепляется к чужому запуску. Envelope содержит worker, taskId, observedAt и log либо report. Чтение разрешено также для dry-run/apply/verify, их запуск допускается отдельными действиями с проверенными checkpoints (см. ниже). Ошибка JSON/I/O/таймаут передаётся обычным результатом ошибки; следующий запрос выполняет только оператор.

Проверки: [модель](../tests/task-observation.test.cjs), [allowlist и смена задачи](../tests/authorities.test.cjs), [Electron и loopback SSH](../tests/workflow-desktop.test.cjs). Desktop-тест моделирует dry-run/apply/verify ответами локальной фикстуры, проверяет отсутствие счётчика до отчёта, поздравление после verify и сохранение истории после перезагрузки. Рабочий сервер, Docker и БД не используются.

## Изменение ширины терминала

[TerminalDivider](../src/TerminalDivider.tsx#L5) расположен между main-content и TerminalPane. Pointer capture удерживает перетаскивание за пределами узкой границы; pointerup/cancel/lostcapture снимают режим resize. `sync` ограничивает ширину минимумом терминала и доступным местом с учётом min-width основной области, применяет inline width и обновляет доступное значение ARIA. ResizeObserver родителя пересчитывает ограничение при изменении окна. Существующий ResizeObserver xterm выполняет fit и PTY resize, SSH-подключение при этом не пересоздаётся.

`save` сохраняет только число пикселей в localStorage (`svetoch.terminal.width.v1`); эффект при открытии восстанавливает допустимое число, при недоступном хранилище используется CSS-ширина. При сужении окна исходное предпочтение сохраняется для последующего расширения. Стрелки влево/вправо меняют размер на 20 px, Home/End выбирают границы. Двойной щелчок сбрасывает сохранённую ширину. Очистка эффекта отключает observer и убирает inline width; `stop` завершает drag и сохраняет ширину.

Нижняя подсказка терминала и его заголовки имеют `flex-shrink:0`; сжимается только SSH/командная область (`flex:1 1 0; min-height:0`). Нижний padding SSH-поверхности и внешние отступы подсказки оставляют место между последней строкой и предупреждением. Вывод команд прокручивается внутри своей области. Это сохраняет границы текста при узком терминале и уменьшении высоты окна.

Внутренний `.terminal-host` не содержит padding: именно его измеряет FitAddon. Отступы принадлежат внешнему `.terminal-surface`, иначе addon учитывает высоту с padding как полезную и последняя строка оказывается ниже доступной области. ResizeObserver и ref терминала привязаны к внутреннему host.

<a id="database-password"></a>

## Сохранение пароля БД

По прямому запросу пользователя пароль сохраняется локально отдельно от общего профиля. [databasePasswordKey](../src/profile.ts) связывает его с SSH host/port/user и database host/port/name/user, поэтому при переключении подключения чужой пароль не подставляется. `loadDatabasePassword` возвращает строку или пустое значение при недоступности хранилища; `persistDatabasePassword` сохраняет строку без trim, а пустое значение удаляет ключ. Ошибка записи обрабатывается формой: пароль остаётся в памяти текущего подключения, интерфейс сообщает о невозможности сохранения.

App хранит пару key/password и выбирает значение только для актуального ключа; изменение поля сразу сохраняется, кнопка сохранения также записывает его. Поле имеет type=password, без раскрытия текста; пароль не входит в общий экспортируемый профиль, команды worker или журнал терминала. Хранилище localStorage содержит пароль в исходном виде, маскирование относится к полю интерфейса. Эта доработка не перезапускает приложение и не выполняет проверку БД автоматически.

<a id="authority-final-stages"></a>

## Кнопки dry-run, apply и verify

[AuthorityImportPane](../src/AuthorityImportPane.tsx) отображает весь маршрут RSL10. Кнопки доступны при проверенных контейнере/worker, accepting=true, busy=false, отсутствии неопределённого start и подтверждённых предыдущих checkpoints. Профиль хранит analysisReportRsl10, dryRunReportRsl10, applyReportRsl10; автоматическое заполнение выполняется только после ручного чтения успешного отчёта. Старые профили получают пустые новые поля из defaults. Путь можно восстановить вручную, его содержимое всё равно перепроверяется backend. Изменение пакета сбрасывает checkpoints. Уже подтверждённые analyze/dry-run/apply не запускаются повторно кнопкой.

`runAuthorityAction` разрешает dry-run-rsl10/apply-rsl10/verify-rsl10. Перед start проверяются контейнер, свежий worker, неопределённый запуск, UUID и сохранённый stage с manifest RSL10. Вложенный `read` читает только JSON из `/work/reports`. Для всех финальных стадий читается сохранённый анализ; `validateImportAnalysis` требует kind=authorities, тот же ID, ready=true, 64 hex-символа approval, корректное число rows и отсутствие ненулевых препятствий. Для apply/verify дополнительно читается dry-run. `validateImportOutcome` требует тот же approval, verified=true, точные status и dryRun; для verify также подтверждается applied-отчёт. Ошибка любого условия возвращается до start. Успешный предыдущий apply того же ID или сохранённый apply checkpoint блокируют повторную запись.

Dry-run/apply передают worker `--approval` из перечитанного отчёта, а не свободный текст UI; verify передаёт только import ID. Механизм uncertainStarts обслуживает новые действия так же, как stage/analyze: неизвестный исход не повторяется без ручного status. Ответ start должен содержать новый task.id, ожидаемый stage и importId; это подтверждает принятие, а не commit. Проверки на стороне самого загрузчика (свежие кандидаты, транзакция, rollback/commit и verified) остаются авторитетными.

При чтении task-report envelope связывает артефакт с задачей до/после чтения. Checkpoint выдаётся только для успешного completed/exit 0, соответствующего выбранному import ID и stage RSL10. Готовый analyze сохраняет путь и сбрасывает downstream dry-run/apply; ready=false очищает checkpoint без продвижения. Подтверждённый dry-run сохраняет свой путь, applied — свой. `checkpointUpdates` обрабатывается AuthorityPane.onUpdate и обычным автосохранением. Отчёты других импортов доступны в наблюдении, но не открывают следующий этап этого RSL10. Фактический отчёт в IPC сохраняется отдельно от дополнительных preflight-read результатов.

UI не выполняет автоматических переходов и не запускает задачи при открытии приложения, смене настроек или по таймеру. Нажатие кнопки «Загрузить RSL10 в public» выполняет реальную запись; dry-run откатывает её. Кнопка verify проверяет результат, затем наблюдение показывает подтверждённое количество и финал. Контракты счётчиков и праздника описаны выше в наблюдении.

Изолированная проверка: authorities.test.cjs проверяет все новые start-действия, ID/approval, препятствия и повторный apply; workflow-desktop.test.cjs проходит все пять стадий через кнопки в отдельном Electron с localhost sshd/фиктивным worker. Рабочий сервер и реальная БД при проверке не используются; пользовательское окно не перезагружается.

При успешном task-report после всех служебных перечитываний checkpoint в поток stdout повторно добавляется исходный отчёт текущей задачи с явным заголовком «ОТЧЁТ ТЕКУЩЕЙ ЗАДАЧИ», task.id, этапом и путём. Данные берутся из уже прочитанного `data`, дополнительного SSH/Docker exec нет. Это предотвращает ошибочное восприятие последнего служебного cat stage/analysis как итога verify/dry-run. При ошибке проверки итоговая успешная секция не печатается. Регрессионный тест проверяет последний stdout и отсутствие повторного чтения verify-файла.

<a id="authority-libraries"></a>

## Независимые маршруты RSL10, RSL11 и TST11

`AuthorityImportPane` заменяет специализированную карточку RSL10: переключатель выбирает processing.library, а `fields/current` отображают только ключи выбранного суффикса Rsl10/Rsl11/Tst11. Для всех библиотек есть package/importId/stageReport/analysisReport/dryRunReport/applyReport. `resetFrom` при ручном изменении поля очищает только его последующие checkpoints в той же библиотеке. Старые настройки RSL10 сохраняются, недостающие поля RSL11 и library берутся из defaults. Выбор библиотеки сам не вызывает IPC и не запускает задачу. Незавершённые команды блокируют переключатель.

Backend settings принимает только RSL10/RSL11/TST11, извлекает общие canonical package/importId/report поля из выбранного суффикса и оставляет namespace другой библиотеки нетронутым. Финальные действия `stage/analyze/dry-run/apply/verify-rsl11` проходят проверку соответствия processing.library, затем нормализуются в общий внутренний allowlist. Команды worker остаются стандартными: stage/input либо stage/import-id/approval. Имена validateRsl10Manifest/validateRsl10Stage сохранены для совместимости тестов, но они принимают явную library (по умолчанию RSL10); производственные вызовы всегда передают config.library. Manifest другой библиотеки отвергается до start. UUID, approval, dry-run и applied проверяются тем же общим кодом.

CheckpointUpdates используют динамический суффикс, поэтому чтение stage RSL11 не меняет importIdRsl10 или его отчёты. Legacy-поля importIdRsl10/stageReportRsl10 в ответе сохраняются только для RSL10. Отчёты предыдущего импорта доступны в общем наблюдении, но не открывают следующий этап выбранной библиотеки. После успешного authorities-prepare и чтения готового manifest выбранной библиотеки backend сохраняет её task.output как путь пакета и сбрасывает только её дальнейшие checkpoints.

AuthorityPane явно поясняет несовпадение import ID последней задачи worker с выбранной библиотекой. История worker общая для сервера/контейнера: сохранённый verify RSL10 не означает, что RSL11 уже запущен. Проверки изолируют настройки обеих библиотек, блокируют чужой manifest/кнопку, проходят обе полные цепочки в отдельном тестовом Electron и подтверждают, что переключение библиотеки не отправляет команд.

В модели наблюдения task.library выводится из worker/input, manifest отчёта, явного start-действия либо истории того же import ID и сохраняется в whitelist истории. Прогноз группирует задачи по этому признаку: длительность RSL10 не считается выборкой для RSL11.

<a id="authority-batch"></a>

## Три библиотеки и автономная перезагрузка НЗ

[AuthorityImportPane](../src/AuthorityImportPane.tsx) показывает RSL10, RSL11 и TST11.
Каждая вкладка использует свой suffix Rsl10/Rsl11/Tst11 и собственные пакет, importId и отчёты.
Переключение вкладки не запускает команды. Блок одиночной подготовки удалён.
[AuthorityBatchCard](../src/AuthorityBatchCard.tsx) отображает общий статус, подтверждённые
числа и результат verify. Кнопка обновления вызывает batch-status, который читает состояние
контроллера и восстанавливает checkpoints трёх маршрутов. Отсутствующие последующие отчёты
очищаются, чтобы старый apply не выглядел результатом нового импорта.

[authority-batch.mjs](../electron/authority-batch.mjs) запускается внутри текущего контейнера
через `node /work/control/authority-batch.mjs --run`; `--version` проверяет контракт,
`--status` читает JSON без подключения к БД. Скрипт рассчитан на образ auth-docs-relations,
его внутренние модули и pg-copy-streams; локально вне контейнера --run не поддерживается.
Конфигурация `/work/control/authority-batch-config.json` содержит version, replaceAuthorities=true,
закреплённый image и inputs ровно RSL10/RSL11/TST11: library, path под /source, sha256, sourceDate.
Паролей в конфигурации нет: connectDatabase читает смонтированный /run/db.env.

Контроллер выполняет 19 шагов: подготовка трёх файлов, три stage, резервная копия с очисткой,
затем analyze → dry-run → apply → verify каждой библиотеки. Прогресс считается по завершённым
шагам, это не процент обработанных записей. TST11 использует tst11-ng и authority-leader-z;
RSL10 — numeric001, RSL11 — rsl11-nafpn, для последних двух пустой FMT отклоняется.

`save` атомарно заменяет authority-batch.json; `hash` читает файл потоком и считает SHA-256,
не удерживая выгрузку целиком в памяти. `validateReport` проверяет библиотеку и исходный SHA
после подготовки, число строк после stage, отсутствие препятствий и approval анализа,
подтверждённую транзакцию после dry-run/apply и полный existingAuthorities после verify.
`task` проверяет закреплённый образ и свободный worker, отправляет один start и каждые 10 секунд
читает его статус. Потерянный ответ start разрешается чтением статуса, повторного start нет.
Смена ID задачи другим оператором, failed/exitCode != 0 или несовпадение отчёта останавливают цепочку.

`backupAndClear` открывает транзакцию с lock_timeout=5s и statement_timeout=5min,
проверяет отсутствие новых FK к authorities, блокирует таблицу и сохраняет PostgreSQL COPY text
в gzip для authorities, authority_relations и связанных AUT document_relations. Поток COPY проходит
через gzip в файл; чанки не считаются записями. Manifest фиксирует SHA, размер и исходные количества.
Только после успешного сохранения файлов удаляются нормативные записи и их связи. Документы,
экземпляры и остальные связи не удаляются; CASCADE не применяется. Ошибка откатывает очистку,
закрывает соединение и сохраняет failed/error в состоянии. Резервная копия находится в
`/work/backups/authorities-<run-id>`; восстановление не запускается автоматически.

Каталог authority-batch.lock защищает от второго контроллера. Перед одиночным start приложение
проверяет отсутствие этого каталога. Контроллер независим от SSH/окна приложения, но остановка
самого контейнера прерывает его. После аварии контейнера старые running/lock нужно сопоставить
с worker и БД вручную; автоматического возобновления и повторной очистки нет. После ошибки
уже подтверждённые apply остаются в public; состояние и backup сохраняются для диагностики.
Финальная проверка сверяет точные количества всех трёх библиотек и отсутствие лишней библиотеки.
