# Нормативные записи: сценарий оператора

Приложение управляет переносом из АЛЕФ в АБИС «Светоч». Соседний `rsl-abis-service-v2` обслуживает АБИС; обработка миграции выполняется серверным `auth-docs-relations-worker`. Эта инструкция описывает интерфейс и команды, а не подтверждает выполнение на рабочем сервере.

<a id="settings"></a>

## Подключение и настройки

В «Подключениях» укажите SSH-сервер, пользователя и приватный ключ без `.pub`, откройте SSH и завершите вход в терминале справа. Отдельные команды используют управляющий сокет того же подключения. Состояние открытого терминала не используется как shell для кнопок.

Изменения профиля сохраняются автоматически в `localStorage`, ключ `svetoch.migration.profile.v1`. Пароль БД в сохранённый профиль не входит. [loadProfile](../src/profile.ts#L16) восстанавливает известные строковые поля; [persistProfile](../src/profile.ts#L33) исключает неизвестные значения и сохраняет эффективные пути. Ошибка чтения профиля возвращает исходные настройки. [effectiveSources](../src/profile.ts#L7) заменяет пустые и пробельные пути значениями [shared/defaults.json](../shared/defaults.json#L1), совпадающими с placeholder.

Пути источников относятся к серверу. `containerPath` переводит их по Docker mounts внутрь `/source`; отсутствие подходящего mount останавливает запуск. Настроенный каталог экспорта не перенастраивает worker: реальная задача создаёт пакет в `/work/output/<task.id>`, а интерфейс показывает соответствующий путь сервера, когда доступно отображение mount.

<a id="container"></a>

## Шаг 1: проверка контейнера

Откройте папку «Нормативные записи». «Статус контейнера» читает `docker inspect`, «Статус worker» — `rsl-aut worker status`. Для перехода к процессингу контейнер должен работать, а ответ worker иметь известный формат. «Статус доставки» читает watcher; «Команды образа» показывает help установленной версии. Эти проверки не запускают импорт и не перезапускают контейнер.

<a id="prepare"></a>

## Шаг 2: процессинг

### Выбор RSL10 / RSL11 / TST11

Вверху блока загрузки выберите RSL10, RSL11 или TST11. Переключение меняет пакет, ID и отчёты всех пяти стадий; результаты другой библиотеки сохраняются отдельно. По умолчанию пути готовы для `/work/output/authorities-2026-10-22/RSL10` и `/RSL11`, `/TST11`. Если пакет уже подготовлен, достаточно «Проверить пакет RSL11», затем «Загрузить RSL11 в staging»; повторять подготовку DAT не требуется. Для каждого этапа доступны те же кнопки анализа/dry-run/public/verify с названием выбранной библиотеки.

Кнопки наблюдения всегда читают последнюю задачу worker, а не запускают выбранную библиотеку. Если после переключения на RSL11 последним остаётся verify RSL10, интерфейс выводит отдельное пояснение. Для начала RSL11 используйте готовый пакет и кнопку stage. После успешной подготовки и чтения отчёта путь нового пакета автоматически попадёт только в настройки выбранной библиотеки.

Следующий раздел показывает пример RSL10; для RSL11 и TST11 порядок идентичен, но все поля и проверки изолированы по библиотеке.

### Готовый пакет RSL10: staging и кандидаты

Для продолжения уже подготовленного пакета используйте карточку «RSL10: загрузка и проверка». Путь пакета по умолчанию — `/work/output/authorities-2026-10-22/RSL10`; допускается путь сервера, доступный через mounts worker. «Проверить пакет RSL10» читает manifest и требует полный готовый пакет RSL10: `kind=abis-authorities`, `version=1`, `complete=true`, `limited=false`, `ready=true`.

«Проверить БД worker» выполняет `import check-db`. Эти операции используют соединение, с которым уже работает worker: пути `--db-env` и `--profile` берутся из Docker command, по умолчанию `/run/db.env` и `/run/import-profile.json`. Настройки подключения из интерфейса предназначены для отдельного теста соединения; пароль интерфейса в команды worker не передаётся.

«Загрузить RSL10 в staging» повторяет проверки manifest, БД и свободного worker и запускает `worker start --stage stage --input <package>`. Этап пишет промежуточные таблицы. После завершения нажмите «Отчёт обработки»: только успешный `completed` с `exitCode=0` и отчёт `kind=authorities`, `status=prepared`, валидный UUID и manifest RSL10 позволяют сохранить ID импорта и путь отчёта в профиль. Затем «Анализировать кандидатов RSL10» повторно проверяет отчёт и запускает `worker start --stage analyze --import-id <UUID>`. Проверяйте статус, лог и отчёт каждой задачи. Автоматического перехода между этапами нет. После анализа доступны кнопки dry-run, apply и verify (см. ниже).

### Подготовка исходных выгрузок

Одиночные кнопки подготовки убраны. Общая перезагрузка всех трёх файлов выполняется
[автономным контроллером](architecture.md#authority-batch), который сначала проверяет
SHA всех источников и подготавливает все пакеты/staging, затем резервирует и заменяет НЗ.
Кнопка «Обновить общую загрузку» показывает прогресс и переносит checkpoints во вкладки.

## От анализа до итоговой проверки

1. После успешного анализа нажмите «Отчёт обработки». Путь отчёта сохранится автоматически, откроется **«Пробная загрузка RSL10»**.
2. Нажмите эту кнопку. Она берёт ID и approvalSha256 из подтверждённого анализа, запускает dry-run. Дождитесь completed / exit 0 и прочитайте отчёт: требуются status=dry-run, dryRun=true, verified=true и тот же approval. Данные public после пробной транзакции откатываются.
3. Откроется **«Загрузить RSL10 в public»**. Это реальная запись нормативных записей, а не проба. Backend повторно читает отчёты stage, анализа и dry-run; сам загрузчик повторно пересчитывает кандидатов в транзакции. При изменении кандидатов требуется новый анализ. Кнопку нажмите один раз.
4. После completed / exit 0 нажмите «Отчёт обработки». Только status=applied, dryRun=false, verified=true для того же импорта и approval подтверждают запись. Количество добавленных НЗ появится в наблюдении; повторная кнопка apply блокируется.
5. Нажмите **«Проверить результат RSL10»**. После завершения прочитайте отчёт verify. При verified=true и подтверждённом apply этого импорта появится праздничный финал.

Пути анализа/dry-run/apply сохраняются в localStorage и видны в свёрнутом блоке «Подтверждённые отчёты». Если приложение обновлено после уже выполненного анализа, достаточно получить статус текущей задачи и прочитать её отчёт — повторно анализировать не нужно. Для восстановления другого этапа можно указать путь ранее созданного отчёта, backend заново прочитает файл и проверит ID/approval/тип результата; введённый путь сам по себе не является разрешением записи. Поле исходного stage остаётся обязательным для подтверждения библиотеки RSL10. Изменение пакета сбрасывает все checkpoints.

## Наблюдение: одна карточка вместо трёх отдельных результатов

«Обновить статус задачи» обновляет состояние, время начала/окончания и длительность. Часы в карточке идут каждую секунду локально; сервер автоматически не опрашивается. «Последние 100 строк лога» добавляет раскрываемый фрагмент с временем чтения. «Отчёт обработки» дополняет ту же задачу счётчиками и итогом этапа. Полный JSON и поток команд остаются в правом терминале. Ошибки не скрываются.

Прогноз использует до пяти успешных запусков того же этапа и источника. Пока история отсутствует, индикатор неопределённый; процент по времени подписан как оценка и не означает долю обработанных строк. Если прогноз превышен, обновите статус. После завершения длительность фиксируется по серверному finishedAt.

На общей временной шкале показаны последние шесть наблюдавшихся задач. Нажатие на строку открывает сохранённую карточку; три кнопки по-прежнему читают текущую задачу worker. Под графиком серым показана следующая операция. История до 40 задач сохраняется между запусками приложения отдельно для каждого сервера и контейнера, без логов. Задачи, которые приложение ещё не наблюдало, автоматически не подгружаются.

После чтения успешного отчёта apply появляется число реально добавленных нормативных записей в public; dry-run показывает откат и нулевую загрузку. После соответствующей итоговой проверки verify появляется поздравление с коротким конфетти. Это подтверждает завершение данного импорта НЗ, а не всех остальных миграций и связей. Все этапы запускаются соответствующими кнопками в разделе «RSL10: загрузка и проверка».

## Ответственность и диагностика

[AuthorityPane](../src/AuthorityPane.tsx#L39) управляет шагами, доступностью кнопок и отображением результата. Вложенный `run` отправляет ограниченное действие через preload и IPC, отсеивает устаревшие ответы после смены профиля и показывает ошибку при потере результата. Изменение SSH или имени контейнера сбрасывает готовность. Ответы для устаревших настроек игнорируются; сохранение ID из отчёта не сбрасывает уже проверенную готовность.

[runAuthorityAction](../electron/authorities.cjs#L239) проверяет профиль, выбирает разрешённую команду, выполняет preflight и проверяет ответ запуска. `settings` нормализует пути и имена контейнеров; `parseJson` отвергает не-JSON ответы; `workerState` проверяет обязательные флаги worker; `reportPath` ограничивает чтение логов и отчётов. [validateRsl10Manifest](../electron/authorities.cjs#L117) проверяет готовность полного пакета, [validateRsl10Stage](../electron/authorities.cjs#L128) связывает отчёт с подтверждённым UUID, [packagePath](../electron/authorities.cjs#L182) разрешает путь пакета внутри worker, [workerDatabasePaths](../electron/authorities.cjs#L212) извлекает разрешённые пути файлов подключения из command контейнера. Ошибки этих функций останавливают операцию до запуска задачи; интерфейс показывает сообщение и фактический вывод команд. Точки определения и актуальные контракты также описаны в [архитектуре](architecture.md#authority-commands).

[runRemoteCommand](../electron/remote.cjs#L13) открывает отдельный SSH-канал через существующий master, передаёт argv с POSIX-экранированием и отдаёт stdout/stderr во вкладку «Команды». Результат содержит `ok`, `exitCode`, `durationMs`, `command`, stdout и stderr. Тайм-аут, прерывание или превышение лимита вывода завершают локальное ожидание; серверная задача могла продолжить работу. При неопределённом ответе start повторный start блокируется до чтения актуального worker status. Проверьте ID и состояние перед повторным запуском. Закрытие приложения не является отменой задачи на сервере.

<a id="verification"></a>

## Изолированная проверка

[workflow-desktop.test.cjs](../tests/workflow-desktop.test.cjs#L11) запускает настоящее окно Electron и локальный `sshd` на случайном loopback-порту. SSH ForceCommand моделирует ответы Docker и worker; рабочие серверы, Docker и PostgreSQL не используются. Проверяются автосохранение без кнопки, хранение пароля отдельно от профиля и восстановление значения, восстановление ключа, default RSL10 path, шаги проверки, наличие вкладки TST11 и отсутствие одиночных кнопок подготовки, статус, лог и отчёт, проверка пакета и БД, staging с сохранением подтверждённого UUID и анализ кандидатов. В `finally` закрываются окно и sshd и удаляется временный профиль. Это подтверждает цепочку UI → IPC → SSH, но не поведение реального Docker-образа и не фактическую миграцию данных.

После сборки интерфейса проверка запускается командой `node --test tests/workflow-desktop.test.cjs`.
